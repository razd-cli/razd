# razd shell activation breaks when the activation script is wrapped in eval

**Date:** 2026-08-11 21:24
**Files:** internal/cli/cmd_shell.go, internal/cli/cmd_shell_test.go
**Severity:** high

## Problem

`razd shell` (interactive subshell mode, added in `cc9fa19`) launched bash/zsh
with the provisioner's activation script wrapped in `eval "..."`. On WSL with
mise, the shell failed to activate:

```
bash: eval: line 198: conditional binary operator expected
bash: eval: line 198: syntax error near `"_mise_hook_prompt_command"'
bash: export: `Files/dotnet/...': not a valid identifier
```

The mise hooks (`_mise_hook_prompt_command`) were never defined, so the
provisioner environment was not active inside the subshell.

## Root Cause

`activationStartup()` in `internal/cli/cmd_shell.go` wrote the entire
multi-line activation script (e.g. `mise activate bash`, 130+ lines) into the
rcfile as a single `eval "..."` string. `eval` re-parses that string in the
**outer** context, so:

- Positional parameters (`$1`, `$@`) expand to empty before the script runs.
  mise's activation uses `[[ $1 != "x" ]]` guards, which then become
  `[[ != "x" ]]` → `conditional binary operator expected` / syntax error.
- PATH entries containing spaces (WSL `/mnt/c/Program Files/...`) are split
  into separate `export` arguments → `not a valid identifier`.

The `eval "..."` wrapper was an attempt to inline the script, but it changed
the parsing context. The script was already being written to a file that bash
`--rcfile` / zsh `ZDOTDIR` sources directly — the wrapper was both unnecessary
and harmful.

## Solution

Write the activation script **verbatim** to the temp rcfile and let the shell
source it directly (bash `--rcfile`, zsh `ZDOTDIR`). No `eval` wrapper. This
preserves the script's own parsing context: positional params stay intact and
PATH entries with spaces survive.

```go
// bash
tmp.WriteString(activation)  // was: eval "<escaped script>"
// zsh
os.WriteFile(rc, []byte(activation), 0644)  // was: eval "<escaped script>"
```

Added `TestActivationStartup_Bash_PathWithSpaces`, which runs the generated
rcfile in a real bash and asserts a PATH entry with spaces survives and a
function using `[[ $1 != "x" ]]` is defined. It failed before the fix with the
exact reported error and passes after.

## Prevention

- When injecting a shell script into a startup file, write it verbatim and let
  the shell source it — never re-wrap in `eval "..."`, which changes the
  parsing context (positional params, word splitting).
- Regression tests for shell activation should **execute** the generated
  startup file, not just assert argv structure. A single-line activation
  passes under `eval`; only a multi-line script with `$1`/`$@` and
  space-containing paths reproduces the bug.
- Test on WSL-style paths (`/mnt/c/Program Files/...`) where PATH entries
  contain spaces.
