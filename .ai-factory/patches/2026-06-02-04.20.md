# Trust decision not persisted after interactive prompt

**Date:** 2026-06-02 04:20
**Files:** internal/trust/check.go, internal/cli/helpers.go
**Severity:** high

## Problem

`razd run` (and other commands) showed the "Trust this project?" prompt every time, even after the user had already confirmed trust. The trust decision was never saved to the trust store.

## Root Cause

`EnsureTrusted()` in `check.go` returned `true` when the user confirmed trust via prompt or `--yes` flag, but never called `Trust()` to persist the decision to `trust.json`. The `ensureTrusted()` wrapper in `helpers.go` had a fallback for `--yes`, but it was unreachable because `EnsureTrusted()` already returned `true` for auto-trust.

The flow was:
1. `EnsureTrusted()` returns `(true, nil)` for autoTrust or PromptTrusted
2. `ensureTrusted()` checks `if !trusted` — never enters the block
3. Trust never gets saved → next run prompts again

## Solution

Modified `EnsureTrusted()` to accept a `Provisioner` parameter and call `Trust()` to persist the decision before returning. This ensures trust is saved in all cases:
- Interactive "Yes" prompt → persists
- `--yes` auto-trust → persists
- `Trust()` also syncs with provisioner (e.g., `mise trust`)

Added `trust.Provisioner` interface to avoid import cycle between `trust` and `provisioner` packages. Simplified `ensureTrusted()` in helpers.go by removing the now-redundant fallback.

## Prevention

- When adding prompt/confirmation flows, always persist the decision — not just return the result
- Test interactive flows end-to-end: confirm the store/save is called, not just the return value
- Check that the "unreachable code" path is actually reachable when designing fallthrough logic
